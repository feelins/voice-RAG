### 第一部分：系统架构与全景介绍（20分钟）

#### 1.1 为什么需要"会说话的人文智能体"？
```
传统问题：
  - 古籍数字化后，如何让更多人能"问到"、"听到"？
  - 研究者需要快速检索，但不是每个人都会高级检索语法
  - 视障人士、老年人、学生需要更友好的交互方式

解决方案：
  - 语音输入：自然、便捷
  - 智能检索：理解问题意图
  - 语音输出：听得见、听得懂
```

#### 1.2 系统架构总览
```
用户说话（麦克风）
    ↓
① 语音识别（ASR）—— 听懂问题
    ↓
② 问题理解 & 知识检索（RAG）—— 找到答案
    ↓
③ 大模型生成（LLM）—— 组织答案
    ↓
④ 语音合成（TTS）—— 说出答案
    ↓
用户听到答案（扬声器）+ 看到出处（屏幕）
```

**关键设计原则：**
- 每个环节都要可降级（API 失败时的兜底）
- 全程可溯源（答案必须标注出处）
- 低延迟（端到端 < 10秒）
- 成本可控（云端 API + 本地混合）

#### 1.3 技术选型对比

| 环节 | 方案 A | 方案 B | 选择理由 |
|------|--------|--------|----------|
| 语音识别 | 阿里云 DashScope | 讯飞开放平台 | 对比两家效果 |
| 知识库 | FastGPT | 自建向量库 | FastGPT 更易用 |

### 第二部分：FastGPT 知识库搭建（30分钟）

#### 2.1 什么是 RAG（检索增强生成）？
```
问题：大模型会"幻觉"（编造不存在的内容）
解决：让模型只根据知识库中的真实内容回答

RAG 流程：
  用户提问 
    → 理解问题意图
    → 在知识库中检索相关文档
    → 将检索结果交给大模型
    → 大模型基于检索结果生成答案
    → 答案标注出处
```

#### 2.2 FastGPT 知识库配置

**第一步：准备语料**
```
格式要求：
  - 纯文本 (.txt) 或结构化数据 (.csv, .json)
  - 每个问答对或文档片段独立
  - 包含元数据（书名、章节、作者、朝代）

示例：
问题：学而时习之是什么意思？
答案：「学而时习之」出自《论语》学而篇。「学」是学习...
出处：《论语·学而第一》
```

**第二步：上传到 FastGPT**
```
1. 登录 FastGPT 平台
2. 创建知识库：名称"古籍问答库"
3. 上传语料文件
4. 设置切分策略：
   - 按句切分 or 按段切分
   - 切分长度：建议 500-1000 字符
   - 重叠长度：100-200 字符
5. 选择向量模型：text-embedding-v3
6. 等待向量化完成
```

**第三步：配置检索策略**
```
混合检索（推荐）：
  - 向量检索：语义相似度匹配
  - 关键词检索：BM25 精确匹配
  - 重排序：bge-reranker-v2-m3
  
检索参数：
  - Top-K：5-10 条
  - 相似度阈值：0.6-0.7
  - 是否返回原文：是
```

**第四步：测试检索效果**
```
测试问题：
  1. 学而时习之是什么意思
  2. 孔子的主要思想
  3. 诗经中有哪些著名篇目

评估指标：
  ✓ 检索到的内容是否相关
  ✓ 排序是否合理
  ✓ 是否包含完整上下文
```

#### 2.3 知识库优化技巧

**处理古籍特殊问题：**
```
1. 繁简转换：
   - 统一为简体或繁体
   - 保留异体字对照表

2. 人名地名处理：
   - 建立实体词表
   - 标注元数据（朝代、地理位置）

3. 同义词扩展：
   - "学而时习之" = "学习并时常温习"
   - 增加白话解释

4. 断句处理：
   - 保留原始古文断句
   - 提供现代标点版本
```

```python
def find_answer(question):
    """混合方案：知识库 + LLM 理解"""
    
    # 第一层：精确匹配
    result = exact_match(question)
    if result:
        return result
    
    # 第二层：模糊匹配
    result = fuzzy_match(question)
    if result:
        return result
    
    # 第三层：LLM 理解
    result = llm_understanding(question)
    if result:
        return result
    
    # 兜底回答
    return default_answer()
```

### 第四部分：古籍语音合成的坑点与优化（30分钟）

#### 4.1 常见问题案例

**问题 1：多音字识别错误**
```
句子：学而时习之，不亦说乎？
问题："说"应读 yuè，但识别/合成为 shuō

原因：
  - ASR 根据现代语境，倾向识别为"说话"的"说"
  - TTS 没有古文上下文，默认读现代音

解决方案：
  方案 A：建立古文多音字词典
  方案 B：使用 SSML 标注读音
  方案 C：LLM 预处理，替换为拼音标注
```

**问题 2：同音字误识别**
```
用户说：学而时习之是什么意思
识别成：学而实习之是什么意思（"时"→"实"）

影响：
  - 知识库匹配失败
  - 返回"无法回答"

解决方案：
  三层匹配策略：
    1. 精确匹配（失败）
    2. 模糊匹配（失败）
    3. LLM 理解问题意图（成功）
       → "实习"在古文语境中应该是"时习"
       → 找到正确的知识库条目
```

**问题 3：通假字读音**
```
句子：有朋自远方来，不亦乐乎
问题："乐"应读 yuè（同"悦"），但读成 lè

解决方案：
  建立通假字对照表：
    说 → yue4
    女 → ru3（同"汝"）
    知 → zhi4（同"智"）
```

**问题 4：断句和停顿**
```
句子：民可使由之不可使知之
问题：
  - 断句不同，意思完全不同
  - TTS 缺少合适的停顿

解决方案：
  添加 SSML 标记：
    民可，使由之；<break time="800ms"/>
    不可，使知之。
```

```python
import websocket
import hashlib
import base64
import hmac
import json
from datetime import datetime
from urllib.parse import urlencode

def synthesize_with_xunfei(text, voice='xiaoyan'):
    """讯飞 TTS 接口"""
    url = create_xunfei_url()
    ws = websocket.create_connection(url)
    
    data = {
        "common": {"app_id": XUNFEI_APP_ID},
        "business": {
            "aue": "lame",
            "auf": "audio/L16;rate=16000",
            "vcn": voice,  # 发音人
            "speed": 50,   # 语速
            "volume": 50,  # 音量
            "pitch": 50,   # 音调
        },
        "data": {
            "status": 2,
            "text": base64.b64encode(text.encode('utf-8')).decode()
        }
    }
    
    ws.send(json.dumps(data))
    
    audio_data = b''
    while True:
        result = ws.recv()
        response = json.loads(result)
        
        if response['code'] != 0:
            break
            
        audio = base64.b64decode(response['data']['audio'])
        audio_data += audio
        
        if response['data']['status'] == 2:
            break
    
    ws.close()
    return audio_data
```

#### 7.1 错误处理与降级方案

**常见错误场景：**
```
1. API 调用失败
   → 重试 3 次
   → 切换到备用引擎
   → 返回友好错误提示

2. 网络断开
   → 切换到本地模型
   → 或提示"请检查网络"

3. 音频格式错误
   → 前端自动转换
   → 后端验证并拒绝无效格式

4. 知识库无匹配结果
   → 返回"抱歉，暂时无法回答"
   → 不要让模型编造答案

5. 麦克风权限被拒绝
   → 降级为文字输入
   → 保留语音输出
```

**降级策略代码：**

```python
    try:
        # 尝试主引擎（阿里云）
        return synthesize_with_aliyun(text, voice_type)
    except Exception as e:
        logger.warning(f"阿里云失败: {e}")
        
        try:
            # 降级到讯飞
            return synthesize_with_xunfei(text, voice_type)
        except Exception as e:
            logger.error(f"讯飞也失败: {e}")
            
            # 返回默认音频或文字
            return get_default_audio()
```

#### 7.2 性能优化

**端到端延迟分解：**
```
用户说完话
  ↓ VAD 检测：200-500ms
  ↓ 音频上传：100-300ms
  ↓ ASR 识别：1-3秒
  ↓ 知识库检索：100-500ms
  ↓ LLM 生成：2-4秒
  ↓ TTS 合成：2-4秒
  ↓ 音频下载：100-300ms
总计：6-12秒
```

**优化方向：**
```
1. 并行处理
   - ASR 识别同时预热知识库
   - TTS 合成时前端显示文字

2. 缓存策略
   - 常见问题预生成音频
   - 缓存检索结果（5分钟）

3. 流式处理
   - 使用流式 TTS
   - 边生成边播放

4. 本地化
   - VAD 在客户端
   - 音频转换在客户端
   - 减少网络传输
```

#### 7.3 成本控制

**API 调用成本估算：**
```
阿里云通义千问：
  - ASR：¥2.5/小时音频
  - LLM：¥0.008/1K tokens
  - TTS：¥2/万字符

月成本估算（日均 1000 次问答）：
  - ASR：1000次 × 10秒 × ¥2.5/3600秒 × 30天 ≈ ¥21
  - LLM：1000次 × 200 tokens × ¥0.008/1K × 30天 ≈ ¥48
  - TTS：1000次 × 100字 × ¥2/万字 × 30天 ≈ ¥60
总计：约 ¥130/月

节省成本的方法：
  1. 使用免费额度
  2. 缓存常见问答
  3. 本地部署开源模型（一次性成本）
  4. 混合架构（云端+本地）
```

#### 7.4 数据安全与隐私

**注意事项：**
```
1. 音频数据
   ✓ 录音后立即删除临时文件
   ✓ 不要永久保存用户录音
   ✓ HTTPS 传输

2. API 密钥
   ✓ 不要提交到 Git
   ✓ 使用环境变量或配置文件
   ✓ 定期轮换

3. 知识库内容
   ✓ 确认数据使用授权
   ✓ 敏感内容脱敏处理
   ✓ 访问日志记录

4. 用户隐私
   ✓ 不记录个人信息
   ✓ 提供隐私政策
   ✓ 支持删除请求
```
